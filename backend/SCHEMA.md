# GEO-SHIELD API data schema

Source status is reported per dataset in `GET /data-sources` and `GET /methodology`; forced or automatic fallback is labeled in the effective API metadata. Geographic point and path coordinates returned for the frontend use WGS84 `[latitude, longitude]` ordering. GeoJSON `geometry.coordinates` follows GeoJSON `[longitude, latitude]` ordering.

- **RiskZone:** `id`, `name`, `description`, `risk_score`, `risk_category`, `population`, `exposed_population`, `factors`, `factor_contributions`, `data_provenance`, `primary_risk_drivers`, `accessibility_factor`, `center`, `coordinates`, and source `geometry`. `elevation_m`, `elevation_risk`, and `elevation_normalization_method` expose elevation feature metadata. `factor_contributions` maps each factor to normalized `risk`, configured `weight`, weighted `contribution` in composite points, `source`, and `status`; rainfall also includes `value_mm`, `unit`, and `period_hours`, elevation includes `value_m`, and water proximity includes nearest-feature `distance_m` where derived. `coordinates` is the Leaflet-ready polygon ring; `geometry` preserves the GeoJSON geometry.
- **Infrastructure:** category arrays `hospitals`, `shelters`, `schools`, `water_bodies`, and `roads`. Features use one `coordinates` field; points contain `[lat, lon]` and paths contain arrays of `[lat, lon]` pairs. `utilities`, `transit`, and `other_critical_assets` are empty unless supplied by the dataset.
- **Resource:** `GET /resources` returns `ambulances`, `boats`, and `shelters`; records have `id`, display name/callsign, status, and `coordinates` in `[lat, lon]` order. Relief kit stock is a separate simulated metric. `/optimize` assignments separate `assigned_zone_id` from map `coordinates`; deployed ambulance/boat assignments include `status: "DEPLOYED"`, `placement_source`, `priority_score`, `risk_score`, `population`, `exposed_population`, `reason`, and `rationale`. Land resources expose `placement_method`, `placement_adjusted`, `placement_distance_m`, `nearest_road_distance_m`, `road_status`, and a `deployment` object. If no dry point can be found within the bounded search, `coordinates` is empty and `placement_failed`/`placement_failure_reason` explain the failure. Boat assignments expose `placement_method` and `water_status`. `reason` values reflect the evaluated zone risk/category, modeled exposure, the zone's listed infrastructure entries, the applicable inventory rule, and placement source. `Active Shelter` describes an existing fixed facility selected for the scenario; it is not a new deployed shelter inventory marker. Fixed infrastructure may have a separate safe `map_coordinates`, `map_placement_method`, `map_placement_distance_m`, `nearest_road_distance_m`, and `road_status`; source `coordinates` remain intact.

- **Route:** `scenario_id`, `origin`, `destination`, `shortest`, `risk_aware`, and `water_checked_endpoints`. Routes use the stored scenario endpoints and the available OSM road graph when the endpoints can connect; otherwise the response identifies a stored modeled fallback. Computed road routes include `route_type`, `road_network_used`, water checks, and geometry length. This is not live navigation or traffic routing.
- **Exposure (`GET /exposure`):** rainfall selection/provenance and `data.hazard`, `data.roads`, `data.facilities`, plus explicit availability records for buildings, settlements, population reporting, land use, and water-body context. The hazard mask is modeled susceptibility cells classified HIGH or CRITICAL. Road lengths use only active real-source OSM line features and are clipped to the recorded OSM query extent; exposed lengths are spatially intersected with the hazard mask. Demo roads are excluded. Facility inventory and intersecting counts are separate, with feature-level source, testable, and exposed fields. Population is not reported as observed exposure.
- **Risk-zone provenance:** evaluated zones include `data_provenance` by factor. The real-elevation grid keeps cell population and non-elevation factors inherited from the Phase 1 mock zones; OSM layers are used only when a retrieved local extract is marked active in the provenance manifest.
- **Study area:** `GET /study-area` reports the configured pilot center and bbox. The current bbox is a rectangle derived from retained demo polygons, not an official boundary.
- **Rainfall:** `GET /rainfall` returns selected `type`, `value_mm`, `source`, `rainfall_source` (`FORECAST`, `SCENARIO`, or `DEMO_FALLBACK`), `period_hours`, `unit`, `accumulation_period`, `retrieved_at`, and `is_real`, plus separate scenario and cached forecast objects. Forecast snapshots are served from local disk, marked stale outside their validity window, and never fetched from the provider during map/API rendering. `POST /simulate` and `/optimize` accept `rainfall_mode: "scenario" | "forecast"`; scenario remains the default. A calculation selects one rainfall input; it never combines the two.
- **Partial OSM coverage:** infrastructure responses retain demo fallback records alongside retrieved OSM features and include a `source_status` on map features. OSM layers report the query extent and source snapshot timestamp; water proximity is OSM-derived only for grid cells inside the retrieved water extent.

## Resource assignment and physical placement

The optimizer is a prototype decision-support heuristic, not a replacement for operational emergency dispatch. It ranks each evaluated zone with `risk_score / 100 × exposed_population / 1,000 × (1.6 − accessibility_factor)`. Ambulances are assigned in descending priority order; boats first target zones meeting the existing water-proximity or drainage threshold, falling back to general priority zones when none qualify. The selected counts are capped by the retained inventory (8 ambulances, 5 boats, 4 demo shelters); zero is a valid selection, including zero active shelters.

Zone assignment is preserved independently of point placement. Land assignments check the selected cell representative point against the mapped water polygons, search for valid land in that cell, and use a bounded nearest-land fallback if necessary. When real OSM road geometries are available, the search favors candidate points within 100 m of a road and reports the measured nearest-road distance; when no real road lines are available, the API explicitly reports `ROAD DATA UNAVAILABLE`. Placement is performed by the backend before map rendering. Fixed facilities retain their input coordinates and expose a separate safe `map_coordinates` field if their source point intersects mapped water.

Boats are not subject to the land-only test. Their placement resolves to a mapped water feature, preferring real OSM water within the assigned zone where available, then the nearest available water feature. If no mapped water feature is available, the original zone representative is retained and labeled `DEMO_FALLBACK` with its water-data limitation. Fixed hospitals, schools, police/fire facilities, and shelters remain facility markers; optimizer ambulance and boat assignments are the only deployed inventory markers. An activated shelter is the same fixed shelter marker highlighted for the scenario, not an additional deployed asset.

Evacuation scenario names and endpoints remain the configured modeled scenarios. When the available OSM snapshot provides a connected path within the endpoint connector limit, `/routes` returns geometry built from mapped road centerlines, screens road segments and endpoint connectors against available mapped water polygons, and reports `route_type: OSM_ROAD_NETWORK`, `road_network_used`, `water_checked`, `water_route_clear`, and per-leg geometry `distance_m`. The alternate path is a geometric preference for clearance from mapped water, not a flood-risk score. Risk scores and travel times are omitted for computed road paths because the old demo values do not describe the returned geometry. If mapped routing is unavailable, the API identifies `MODELED_FALLBACK` and includes a `fallback_reason`; stored fallback lines crossing mapped water are withheld. This remains a prototype, not live navigation, traffic guidance, or a capacity-validated dispatch direction.
